## Context

Мотивация — в [proposal.md](proposal.md).

Сегодня `FileStorageService` хранит `Map<String, FileMetadata> index` в памяти, пишет сайдкар `{id}.meta.json` на каждую загрузку и восстанавливает индекс в `@PostConstruct` через `DirectoryStream` по `*.meta.json`. Содержимое лежит в `{id}.bin`; загрузка идёт «во временный файл → сайдкар → атомарное перемещение», чтобы падение посередине не оставило содержимое без метаданных. Интерфейс `FileStorage` объявляет ровно три метода (`store`, `load`, `listFiles`), и `FileStorageController` работает только с ним.

Спек `file-storage` содержит несколько инвариантов, которые это изменение обязано сохранить дословно: каждый id из списка скачивается, файл без содержимого в списке не появляется, нечитаемая запись метаданных не мешает старту, а неудача при сохранении метаданных не оставляет содержимое в каталоге.

Координаты артефактов сверены с BOM Spring Boot 4.1.1 в локальном репозитории, а не взяты по памяти из Boot 3: в проекте действуют модульные имена стартеров (`spring-boot-starter-webmvc`, `spring-boot-restclient`), и BOM управляет `spring-boot-starter-data-jdbc`, `spring-boot-starter-flyway`, `spring-boot-starter-flyway-test`, `spring-boot-testcontainers`, `org.postgresql:postgresql` 42.7.13, Flyway 12.4.0 и Testcontainers 2.0.5 (где модуль PostgreSQL называется `org.testcontainers:testcontainers-postgresql`, а отдельного `junit-jupiter` больше нет).

## Goals / Non-Goals

**Goals:**
- Сделать таблицу PostgreSQL единственным источником листинга; убрать индекс в памяти и сканирование каталога.
- Завести версионированные миграции в каталоге, куда естественно ложится следующая.
- Не потерять файлы, загруженные до этого изменения.
- Сохранить HTTP-контракт и все существующие тесты, не ослабляя ни одного утверждения.

**Non-Goals:** как в [proposal.md](proposal.md) — содержимое остаётся на диске, API не меняется, удаления, пагинации и поиска нет, уборки осиротевших файлов нет, `auth` не трогаем.

## Decisions

**Flyway, SQL-миграции в `src/main/resources/db/migration`.**
Пользователь выбрал Flyway. Каталог — умолчание Spring Boot, поэтому конфигурации не требуется: `V1__create_stored_file.sql` подхватывается сама. Начиная с Flyway 10 поддержка конкретной СУБД вынесена в отдельный артефакт, поэтому нужно проверить, тянет ли `spring-boot-starter-flyway` за собой `flyway-database-postgresql`, и добавить его явно, если нет. Альтернатива Liquibase отклонена пользователем.

**Таблица `stored_file`.**

```sql
create table stored_file (
    id                varchar(64)  primary key,
    original_filename text         not null,
    content_type      varchar(255),
    size_bytes        bigint       not null check (size_bytes >= 0),
    created_at        timestamptz  not null default now()
);

create index stored_file_created_at_idx on stored_file (created_at, id);
```

Построчно:

- `id varchar(64)`, а не `uuid`. Сейчас id — это `UUID.randomUUID().toString()`, но при переносе с диска приходят id, которые сервис никогда не проверял на формат (тест `FileStorageStartupTest` кладёт сайдкар с id `usable-id`). Колонка типа `uuid` отвергла бы такие записи ровно там, где цель переноса — ничего не потерять. Цена — 36 байт вместо 16 и отсутствие проверки формата на уровне базы.
- `original_filename text not null` — имя уже нормализовано `sanitizeFilename` и пустым не бывает, верхней границы у него нет.
- `content_type varchar(255)` **допускает null**: `validatedContentType` возвращает `null`, когда клиент не объявил тип, и `FileStorageController` уже умеет отдавать такой файл как `application/octet-stream`. `not null` здесь сломал бы существующий сценарий.
- `size_bytes`, а не `size`: `size` — ключевое слово в ряде диалектов, и явное имя избавляет от кавычек в будущих запросах. `FileMetadata.size()` при этом не переименовывается, разницу гасит строка-сущность.
- `created_at` в API не показывается. Он нужен, чтобы у списка появился устойчивый порядок: сейчас `List.copyOf(index.values())` отдаёт порядок хеш-таблицы, то есть произвольный. Спек порядка не требует, так что это усиление, а не изменение контракта. Умолчание — `clock_timestamp()`, а не `now()`: `now()` возвращает время транзакции, поэтому все строки, вставленные одной транзакцией (а перенос вставляет именно так), получили бы одинаковую метку, и порядок свёлся бы к сортировке по id. Это выяснил тест из задачи 3.3, где три вставки в одной транзакции вернулись в алфавитном порядке вместо порядка вставки.

**Отдельная строка-сущность `StoredFileRow`, а не `@Table` на `FileMetadata`.**
`FileMetadata` — это тело ответа API. Повесив на него `@Id` и `@Table`, мы связали бы JSON-контракт со схемой: добавление колонки стало бы изменением API, а `created_at` пришлось бы либо показывать наружу, либо прятать аннотацией. `StoredFileRow(String id, String originalFilename, String contentType, long sizeBytes, Instant createdAt)` живёт в `filestorage.service` рядом с репозиторием, преобразование в `FileMetadata` и обратно — там же.

**Вставка делается явным `@Query`, а не `CrudRepository.save`.**
Ловушка Spring Data JDBC: id присваивается приложением, а не базой, и без `@Version` или реализации `Persistable` сущность с ненулевым id считается уже существующей — `save()` выполнит `update`, тот затронет ноль строк и упадёт. Варианты: реализовать `Persistable<String>` с транзиентным флагом `isNew`, вызывать `JdbcAggregateTemplate.insert()` или объявить в репозитории `@Modifying @Query("insert into stored_file (...) values (...)")`. Выбран третий: запись остаётся неизменяемой без служебного поля, намерение читается прямо в коде, а `created_at` можно не перечислять — сработает `default now()`. Чтение — обычные производные методы `CrudRepository`.

**Репозиторий кладётся в отдельный подпакет `filestorage.repository`.**
Изначально решение было обратным: `repository` нет среди шести подпакетов `project-structure-skill`, а `service` прямо назван местом для внутренних коллабораторов, которыми владеет сервис. Пока шла реализация, пользователь дописал в скилл правило «слой репозиториев и обращения к БД должен быть реализован через компоненты репозитория», то есть сделал доступ к базе отдельным слоем, а не деталью сервиса. Скилл главнее прежнего рассуждения, поэтому `StoredFileRepository` и `StoredFileRow` живут в `filestorage.repository` и публичны — их видит `filestorage.service`. Наружу домена они по-прежнему не выходят: `FileStorage` их не упоминает, а `FileMetadata` собирается в сервисе.

**Порядок операций при загрузке меняется: содержимое публикуется до строки в базе.**
Было: временный файл → сайдкар → атомарное перемещение. Станет: временный файл → атомарное перемещение → вставка строки; при неудаче вставки удаляется `{id}.bin`, при неудаче перемещения — временный файл.

Причина — чем оборачивается падение процесса посередине. При старом порядке «сначала метаданные» падение между вставкой и перемещением оставило бы строку в базе без содержимого, то есть id, который попадает в список, но не скачивается, — прямое нарушение сценария «Listing agrees with download». При новом порядке падение оставляет `{id}.bin` без строки: байты потеряны для системы, но видимое состояние не врёт. Сценарий «Upload fails partway through persisting» сохраняется: при штатной ошибке вставки содержимое удаляется, и в каталоге ничего не остаётся.

**Список фильтруется по наличию содержимого на каждом запросе.**
Инвариант «файл без содержимого в списке не появляется» раньше обеспечивался проверкой при построении индекса. Индекса больше нет, поэтому `listFiles()` после выборки строк проверяет `Files.isRegularFile` для каждой. Цена — один системный вызов на файл за запрос. Альтернатива — сверка один раз при старте — отклонена: она восстанавливает ровно ту зависимость от момента старта, ради ухода от которой всё и делается, и оставляет окно между стартом и исчезновением файла. Если список вырастет настолько, что проверка станет заметной, её место — за пагинацией, которой пока нет.

**Перенос выполняется `ApplicationRunner`, а не `@PostConstruct`.**
Компонент переноса обязан выполняться после Flyway. `@PostConstruct` на бине, зависящем от `DataSource`, такой гарантии сам по себе не даёт, а `ApplicationRunner` работает после полного подъёма контекста, когда миграции заведомо применены. `@SpringBootTest` вызывает runner-ы так же, как обычный запуск, поэтому `FileStorageStartupTest` продолжает проверять то же самое.

**Перенос ничего не удаляет и не переименовывает.**
Сайдкары остаются лежать на диске инертными файлами, а идемпотентность обеспечивается проверкой «строки с таким id ещё нет». Альтернатива — переименовывать перенесённый сайдкар в `.imported` — отклонена: она превращает восстановимую операцию в разрушающую ради выигрыша, которого сейчас нет. Оборотная сторона: когда появится удаление файлов, удалённая строка начнёт воскресать при следующем старте, пока сайдкар лежит на диске. Пока API удаления нет, случай недостижим; это первое, что нужно пересмотреть при добавлении удаления.

**Нечитаемый сайдкар пропускается ровно как сейчас.**
Логика `indexSidecar` — нечитаемый JSON, id, не совпадающий с именем файла, отсутствующее содержимое → предупреждение в лог и пропуск — переезжает в компонент переноса без изменений. Именно поэтому сценарий «Unusable metadata does not prevent startup» остаётся верным и не требует правки основного спека.

**`FileMetadataStore` остаётся, но только на чтение.**
При загрузке файла он больше не вызывается; переносу нужен его `read`. Метод `write` и константы, использовавшиеся только для записи сайдкара, удаляются, если после переноса на них не остаётся ссылок.

**Тесты — один общий контейнер PostgreSQL и отдельная база на каждый тестовый класс.**
`spring-boot-starter-data-jdbc` требует `DataSource` в любом `@SpringBootTest`, включая тесты `auth` и `SkillsKeeperApplicationTests`. Контейнер поднимается один раз на весь прогон статическим синглтоном в `PostgresTestContainer`, а не бином с `@ServiceConnection`: `AuthenticatedApiTest` помечен `@DirtiesContext(AFTER_CLASS)`, поэтому бин-контейнер Spring останавливал бы и запускал заново на каждый из двадцати с лишним классов.

Изоляция классов друг от друга сделана отдельной базой на класс, а не очисткой таблицы. Очистка здесь не работает в принципе: строки появляются во время подъёма контекста, их создаёт перенос метаданных с диска, поэтому уборка после старта удалила бы ровно то, что тест пришёл проверить, а уборка до старта не нашла бы ничего. `@DynamicPropertySource` вызывается один раз на контекст, то есть один раз на класс, — там и создаётся свежая база, в которой Flyway затем строит схему. Вариант с `@Transactional` и откатом не подходит для тестов через MockMvc: запрос идёт в собственной транзакции. Для теста репозитория, который ходит в базу напрямую, `@Transactional` как раз применим и используется.

**Подключение конфигурируется переменными окружения с локальными умолчаниями.**
В `application.properties` — `jdbc:postgresql://localhost:5432/skills_keeper` и учётные данные вида `${SKILLS_KEEPER_DB_PASSWORD:skills_keeper}`, чтобы в репозитории не лежал пароль, пригодный где-то кроме локального `compose.yaml`. Сам `compose.yaml` добавляется как удобство запуска; зависимость `spring-boot-docker-compose` сознательно не подключается, чтобы приложение не поднимало контейнеры само по факту наличия файла.

## Risks / Trade-offs

- [Всем тестам, включая не связанные с базой, теперь нужен Docker] → Прямое следствие требования PostgreSQL и того, что `@SpringBootTest` поднимает полный контекст. Смягчение — один общий контейнер на весь прогон. Если в CI Docker недоступен, это выяснится на первой же задаче, и лучше узнать до реализации, чем после.
- [Падение процесса между публикацией содержимого и вставкой строки оставляет файл, которого никто не видит] → Осознанный размен: видимое состояние никогда не врёт, а потерянные байты убирает будущая уборка, вынесенная в Non-Goals. Старый порядок ронял более важный инвариант.
- [Проверка существования файла на каждый элемент списка — N системных вызовов на запрос] → Приемлемо при нынешних объёмах и точно сохраняет требование спека. Пересматривается вместе с пагинацией.
- [`varchar(64)` вместо `uuid` не даёт базе проверять формат id] → Цена того, что перенос не отвергает исторические записи. Формат id по-прежнему задаётся кодом, который его генерирует.
- [Одна большая правка `FileStorageService`: индекс, сканирование, порядок операций и источник данных меняются разом] → Смягчается порядком задач: сначала инфраструктура и миграция при неизменном поведении, затем перевод чтения, затем записи, и полный прогон тестов после каждого шага.
- [Сайдкары остаются на диске и при появлении удаления начнут воскрешать записи] → Записано выше как то, что нужно пересмотреть первым; сейчас случай недостижим.
- [Точные координаты артефактов Boot 4 могут отличаться от ожидаемых] → Имена сверены с BOM 4.1.1 в локальном репозитории, а задача 1.2 требует подтвердить их сборкой, а не доверием к списку.
